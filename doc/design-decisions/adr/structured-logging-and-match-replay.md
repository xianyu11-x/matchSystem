# 匹配内核的外部日志接入与逻辑节点时间线

2026-11-24 · **已实施**

## 背景

模拟器的 Match 历史记录成功成局的成员。评估新规则时，还要知道该逻辑节点何时接收票据、获得了几次匹配机会，以及何时有人撤票。仅凭成员列表或 Ticket.CreatedAt 无法恢复这些输入与调度时点。

## 决策

1. 在物理节点和独立逻辑节点的创建配置中接入宿主的 `*slog.Logger`。宿主通过 Handler 使用现有日志库，详细录制通过独立开关启用，数据仍写入同一个日志出口。节点序号和业务时点在 owner 协程内确定，异步日志后端接收独立快照。
2. 单个逻辑节点实例是提取和回放的单位。每个实例有独立流标识和连续序号，物理节点转发到逻辑节点的动作只计一次。物理选择器选中该逻辑节点之后才有该部署的执行机会，因此只需录制选中部署实际获得的匹配调用。
3. 时间线按 Ticket 加入、匹配轮次和 Ticket 主动退出理解。每个轮次关联原始 `BeginMatchRound(now)` 及零次或多次 `ProduceMatch`。轮次开始和调用分别增量写入，展开时通过原始序号与票据事件交错。源规则返回的种子尝试数和结果类别可供对照。一轮内发生在两次调用之间的撤票，回放时仍在两次调用之间生效。
4. 主动撤票由宿主在取消排队入口显式标识。通用删除另行分类。每次成功入池都有自己的事件序号，同一 TicketID 再次入池时，历史撤票仍指向原入池代次。新规则已提前将该次入池的票据匹配走时，后续源撤票可记录为已离池。
5. 模拟器负责收集、提取和展示单节点日志，使用规则库中的候选 RuleJSON 建立独立的逻辑节点。先检查时间线完整性、票据属性和 Fact/Provider 契约，再按源顺序执行，轮次使用原始逻辑时间。候选规则的种子选择、匹配成员和 Fact 计算均由新节点完成。
6. 客户端传递导出的原始时间线 JSON，保留 Go int64/uint64 精度。UI、HTTP 和命令行使用同一套模拟器逻辑，避免出现两套兼容性裁决。
7. 模拟器进程保留内存中的近期记录，同时将时间线及 Fact 事件流式写入每次运行独立的 `matchscope-<日期>-<时间>-<随机串>.log` 文件。独立 API 默认使用启动工作目录下的 `Logs/`，桌面 shell 显式指定程序同目录的 `Logs/`；`--log-dir` 支持独立 API 更换目录。无法创建日志时不启动，运行中写入失败则报告并停止磁盘写入，模拟器与内存记录继续运行。
8. 核心时间线及模拟器 Fact 的 slog 消息正文固定为 `[match_replay] ` 加包含 `timeline` 或 `timelineFacts` 的单行 JSON 对象；无标记开关。宿主的 Handler 负责日期、级别等外层，内置模拟器文件的回放行直接从标记开始。提取器兼容历史 JSONL 和外部日志；按可识别边界判定回放事件，损坏记录报告行号。具体边界见[外部日志格式](../../simulator/timeline-replay.md#外部日志格式)。

## 时间和兼容性边界

节点内序号决定同一时点的先后。记录同时区分 Ticket.CreatedAt、实际动作相对于流起点的时间偏移以及当前轮次的业务时间 `now`。候选节点按给定时间线运行，因此能够比较相同来源流量和匹配机会下的表现；物理节点重新分配调度配额、宿主实际 CPU 性能及外部服务墙钟耗时属于其他实验。

宿主日志应全量保留录制事件。丢失的开头或中间记录会破坏关联关系。读取仍在运行的节点时，使用已观察到的连续前缀，导出结果只描述该范围。与历史运行有外部依赖的规则需要可隔离的 Provider 和足够的源输入。事实描述符只描述能力，不能作为历史值使用。

运行方式和首版支持的配置见[模拟器回放指南](../../simulator/timeline-replay.md)。核心 API 见[Go 接入指南](../../match-system/go-consumer.md#记录逻辑节点时间线)。
