# ADR：独立规则库与物理节点部署

- 日期 2026-11-23
- 状态 已实施

## 背景

规则页原先通过修改场景草稿来编辑匹配规则。规则与部署共用一条记录，保存时会构建
新的模拟器运行时。用户需要先自由设计规则，再决定在每台物理节点上装载哪些逻辑节点。

## 建议方案

规则库由模拟器服务持有，以 `RuleID` 标识 `match-rule/v1` 文档。保存规则库时检查
修订号、规则内容和重复身份。库的生命周期独立于场景替换和节点增删，规则文件可通过
导入和导出迁移。初始场景为新服务提供规则库的初始内容，服务进程启动时间提供修订号起点。

节点部署包含逻辑节点身份、规则引用、路由启用状态与权重，以及可选的运行时 Facts 和
Provider。一个逻辑节点装载一条匹配规则，一个物理节点可装载多条这样的部署。已有
部署使用装载时的规则快照，用户在节点部署中显式选择应用规则库版本后才替换快照。
从规则库移除文档时，运行中的节点仍持有已装载的内容。

物理节点编辑复用增量路由，保留规则、Facts 和 Provider 均未变化的逻辑节点及其队列。
移除或重新装载的部署由该次节点变更处理。原有 `simulator-scenario/v1` 仍承载完整的
运行态快照，便于导入旧场景及导出可重放的场景。

网页节点编辑可用 `keepTickFacts` 让服务端按原值保留已有部署的 Tick Facts。该标志允许
在只调整路由时直接沿用完整的 `int64` 和 `uint64` 数据。

## 物理节点更新入口

节点编辑可能同时新增、替换、移除或重排多个逻辑节点。逐项调用单节点更新会把批量提交的
预检和回滚交给宿主。用暂存物理节点可以复用装载流程，但会为同一物理身份额外创建节点和
owner 协程，并要求调用者同步两个节点的轮次。

采用 `PhysicalNode.Reconfigure`，由宿主直接提供预先构建的逻辑实例、最终顺序和可选调度器。
目标 owner 协程统一校验并提交，仅将新增或替换的实例加入活动轮次。模拟器负责准备 Provider 和
路由，并在核心提交成功后发布元数据或在失败时回收新建资源。接入约定见
[PhysicalNode API](../../match-system/code-reference.md#3-physicalnode-api)。

## 约束

同一个物理节点对同一 `RuleID` 只装载一个逻辑节点。同一 RuleID 跨节点部署时，
当前场景的运行副本使用相同规则指纹，展示别名可以不同。需要同时运行两个不同规则
版本时，可以在规则库中用不同 RuleID 保留两份规则，再分别部署。
