# 逻辑节点时间线与替代规则回放

时间线回答一个具体逻辑节点实例在什么时候接收了哪些 Ticket、什么时候开始轮次并执行匹配、哪些 Ticket 在什么时候主动退出。同一条规则部署在多个节点时，每个实例有自己的时间线。

## 自动记录与文件位置

模拟器 API 每次启动都会将运行中的录制记录写入单独的文本日志文件。
Windows 桌面客户端的文件位于 `MatchScope.exe` 同目录的 `Logs/`；独立启动的
`simulator-api` 默认写入进程启动工作目录的 `Logs/`。例如从仓库根目录启动时，目录为
`G:\matchSystem\Logs\`。Web 通过 API 使用相同的录制与回放功能，日志位于 API 进程
所在机器，而不是浏览器所在机器。文件名为 `matchscope-<日期>-<时间>-<随机串>.log`，
日期和时间使用启动时的本地时间；每次启动独占创建新文件，不覆盖以往运行的文件。
每条回放记录单独占一行，以 `[match_replay] ` 开头，后接包含 `timeline` 或
`timelineFacts` 的单行 JSON 对象；回放行不另加日志日期和级别，时间线事件载荷本身保留
录制时间与顺序。整个文件不是 JSON Lines（JSONL）格式。

独立 API 可使用 `--log-dir` 指定其他日志目录：

```powershell
go run ./cmd/simulator-api --addr 127.0.0.1:8080 --log-dir G:\matchSystem\my-logs
```

启动时无法创建目录或日志文件会阻止 API 启动。运行时若磁盘写入失败，API 在标准错误
报告文件可能不完整，并停止写入该文件；模拟器和内存中的近期日志继续运行。正常退出先
结束模拟器，再关闭日志文件。桌面端关闭窗口时直接终止 sidecar，通常没有流结束事件；
已写入的连续前缀仍可用于提取，进程被终止时最后一条记录可能不完整。

在「时间线回放」的「上传日志」中选择自动生成的 `.log` 文件，可从中选择逻辑节点实例并
提取时间线。也可上传历史 JSONL 或包含 `[match_replay]` 标记的宿主日志，格式见下文。提取后手动
保存的时间线 JSON 是某个实例的回放输入，与自动生成的原始日志不同。回放结果是一次候选规则
的评估结果，页面展示结果但不提供保存结果按钮；通过 HTTP
或命令行取得的结果也不是原始日志或时间线。重启服务后可使用已保存的原始日志或时间线
文件继续分析。

上传日志的合计大小上限为 32 MiB。回放需要所选实例从起点开始的连续记录；超过上限时，
应按实例保留完整输入并保证其在大小限制内，不能假定把同一实例的记录按字节任意拆分后
仍可回放。如果单个完整实例已超过 32 MiB，当前接口无法直接导入回放。便携客户端升级后的
历史日志位置见[客户端升级说明](client-build.md#客户端检查更新与便携包升级)。

## 外部日志格式

日志必须为 UTF-8 文本，每个录制事件占一行。新的回放消息正文固定为
`[match_replay] ` 加单行 JSON 对象；核心事件使用顶层 `timeline`，模拟器的 Fact 记录使用
顶层 `timelineFacts`。日志系统可以在正文外添加日期、级别或模块等信息。历史 JSONL
（每行一个 JSON 对象）仍可导入，也可与新格式混用。以下 `{...}` 表示实际完整对象，
只用于展示格式：

```text
[match_replay] {"timeline":{...}}
2026/11/24 17:25:16 [INFO] match.node: [match_replay] {"timeline":{...}}
{"module":"match.node"} | [match_replay] {"timeline":{...}}
[match_replay] {"timelineFacts":{...}}
{"time":"2026-11-24T17:25:16+08:00","level":"INFO","msg":"[match_replay] {\"timeline\":{...}}"}
{"message":"[match_replay] {\"timeline\":{...}}"}
time=2026-11-24T17:25:16+08:00 level=INFO msg="[match_replay] {\"timeline\":{...}}"
time=2026-11-24T17:25:16+08:00 level=INFO msg=[match_replay] {"timeline":{...}}
{"time":"2026-11-24T17:25:16+08:00","level":"INFO","timeline":{...}}
```

兼容历史 JSONL：旧记录即使没有标记，只要包含顶层 `timeline` 或 `timelineFacts`，仍按
原规则读取。标准 slog JSON 外层中的 `msg` 若含完整的新格式回放消息，优先读取消息载荷，
不重复读取该外层可能同时携带的历史字段。外部 JSON 日志也可使用顶层 `message` 字段，
其正文以标记开头并后接有效事件载荷时同样可导入；如果外层存在 `msg` 字段，则忽略 `message`。

带标记的载荷应为包含非 `null` 的顶层 `timeline` 或 `timelineFacts` 的完整 JSON 对象。
标记处于行首或标准日期时间和级别前缀后时，损坏的载荷会报错并指出行号。其他宿主前缀下，
独立标记及其后的上述字段构成回放记录；字段已出现而 JSON 截断也会报告行号。普通文本仅
提及标记、近似标记或标记后的 JSON 不含这两个字段时，不视为回放记录。文本行如果包含与
回放记录完全相同的标记和事件载荷，其字节形式与真实录制行无法区分，也会作为回放记录处理；
业务日志应避免输出这种形式。输入中有明确回放标记消息时，允许前后混入普通宿主文本；
没有此类消息时，仍按历史 JSONL 的规则诊断未知或损坏行，旧版标准日期时间与级别前缀的
普通日志除外。因此，仅含任意普通文本的文件不一定能成功导入。自定义日志接入与标记的生成方式见
[Go 接入指南](../match-system/go-consumer.md#记录逻辑节点时间线)。

## 从时间线评估规则

1. 在规则库保存候选规则。可以复制源规则后修改成局条件、种子顺序、评分或候选预算，并为副本分配独立的 RuleID。
2. 在左侧「时间线回放」选择「当前模拟器」或「上传日志」，选择逻辑节点实例，点击「提取时间线」。检查节点身份、Ticket 加入、撤票和轮次。可将提取结果保存为文件，之后从「载入时间线文件」打开。
3. 选择候选规则。服务端校验属性、Fact 声明和可用的 Provider 配置，通过后创建隔离的逻辑节点执行回放。
4. 对照轮次中的实际调用和候选规则生成的匹配结果。源时间线决定匹配机会，候选规则决定尝试的种子和成局的成员。候选规则提前匹配走某张票时，后续撤票可能遇到已经离池的 Ticket。

轮次记录保留原始 `BeginMatchRound(now)` 和逐次 `ProduceMatch` 调用。节点内序号确定同一时点的先后，空轮也会重置种子流和预算。提取时间线本身可以单独完成。

### 阅读事件时间轴

提取出的源时间线和候选规则的回放结果分别显示为横向时间轴。横轴按相对录制起点的时间
偏移定位，事件类型以不同颜色、符号和泳道区分；显示顺序仍以事件序号为准。时间轴下方的
缩略图始终展示全部时间的事件密度，浅蓝色选区对应上方当前显示的时间范围。

拖动选区两端的手柄可调整起点和终点，拖动选区内部或下方抓手可在保持跨度的同时平移。
选区不会超出完整时间范围；点击「显示全部时间」恢复全域。键盘聚焦手柄或选区后，可用方向键
调整端点或平移，按住 Shift 扩大步长，Home 和 End 可移动到对应边界。只有一个有效时点时
无需调整范围，不显示缩略控件。这些操作只影响当前视图，不会修改原始时间线；源时间线与
回放结果各自保留独立的显示范围。

同一泳道内距离很近或发生在同一时点的事件会合并为带数量的标记，点击标记后可用「上一条」、
「下一条」或「第 N 条」跳转逐条查看；跳转数字是当前事件列表的位置。选中事件后，详情显示
时点、轮次、票据或匹配调用结果；回放成局还显示候选成员及对应源调用的结果和成员，可展开
完整事件。没有可精确使用时间偏移的事件不会绘制在图上，但仍可通过逐条浏览或跳转查看。

## 准备候选规则

例如，保留源规则的 Ticket 属性和 `memberCount` Match Fact，把成组门槛由四人改成两人，就可以观察相同票据及调用机会下的成员组合。若将源数据中的某个数值属性改成字符串列表，或者将同名 Fact 从 Object 改为 Match，则需要先解决输入或 Provider 的不兼容。

有关内置 Fact、规则库和源节点调度的背景，见 [Fact 来源](fact-sources.md)、[规则库操作](rule-forms.md)和[内核运行流程](../match-system/runtime-flow.md)。

默认使用独立的内置 Provider。候选规则如需现有部署的 Python 配置，可选择其部署作为 Provider 来源，由回放单独启动 Worker。依赖宿主登记的 Object Fact 时，日志还须包含对应入池及后续变更的历史输入。进程内自定义 Go Provider 暂无通用的隔离复制方式。

首版按下面的条件判定替换是否成立。

| 检查对象 | 通过条件 |
| --- | --- |
| Ticket 属性 | 候选规则声明的属性在源契约中有同名同类型声明，集合上限可容纳源契约的数据。实际入池的票据还要通过源、目标两份属性校验。 |
| Fact 配置 | 候选规则使用的 Fact 在源配置中具有相同名称、类型、scope 和集合上限。日志需提供候选 Provider 计算这些 Fact 所需的宿主输入。 |
| Provider | 候选节点以目标 Contract 完成握手，使用的 Provider 标识、版本及相应能力与源记录相容。候选组合的 Match Fact 由该节点重新计算。 |

校验失败会报告错误字段或时间线位置。若回放中途遇到两条规则执行结果分化导致的冲突，例如新规则仍保有一个即将再次入池的同 ID 票据，报告会标出中断序号，已执行的动作仍可查看。

## 命令行

先启动模拟器 API。在仓库根目录用以下命令列出保留的实例，随后把示例中的实例标识替换为实际值。
示例规则 `91002` 是[八票 FIFO 规则](../../examples/simulator/fifo-8-match-rule.json)，
使用前需将其导入规则库；也可将规则编号替换为其他已保存的候选规则。

```powershell
go run ./cmd/match-replay extract
go run ./cmd/match-replay extract -instance INSTANCE_ID -output timeline.json
go run ./cmd/match-replay inject -timeline timeline.json -rule 91002
```

从文件提取时给 `extract` 传入 `-logs source.log` 或 `-logs source.jsonl`，使用其他服务地址时传入 `-api`。模拟器保留最近约 32 MiB 的结构化日志，服务重启后可通过已保存的时间线或原始日志再次回放。外部日志和单份时间线各有 32 MiB 大小上限。缺少实例起点、连续序号或入池前史时，根据提示重新选择完整记录。

## HTTP 接入

在运行中的模拟器上调用以下接口。请求与响应均为 JSON，字段的精确类型见 [OpenAPI](../../api/openapi/simulator.yaml)。

| 操作 | 请求 |
| --- | --- |
| 列出录制实例 | `POST /api/v1/replay/extract`，请求体为 `{}` |
| 提取某个实例 | 对同一路径发送 `{"instanceId":"实例标识"}`，读取响应中的 `timelineJson` |
| 提取外部日志 | 对同一路径传入 `logs`，内容为录制文件、带 `[match_replay]` 消息的宿主日志或历史 JSONL。可先列出实例，再带上相同的日志及选定的 `instanceId` 提取 |
| 校验并回放 | `POST /api/v1/replay/run`，传入 `timelineJson` 和规则库中的十进制字符串 `targetRuleId` |

将 `timelineJson` 作为原始字符串保存和转交，能保留完整的 64 位时间、票据身份和属性值。使用 JavaScript 的调用方若先将其解析为 Number 再重新编码，大整数可能失去精度。
